# PIN-0011 — Users, sessions, and the demo provider

**Type:** Feature · **Phase:** 4 · **Status:** Review

Spec: `.codex/specs/auth-and-roles.md` (Q4 resolved — LINE Login is the destination,
password auth skipped entirely).

## Goal
Establish who is calling. Nothing today identifies a caller, so `SHOP_ID = 1` is the only
notion of "whose data this is".

This ticket builds the provider-agnostic half: user and session storage, session
read/create/revoke, a `demo` provider, the login page, and a redirect that makes `/`
require a session. The LINE provider (PIN-0014) plugs into the same seam once เกรพ has a
LINE Login channel.

After this the app requires a session but still reads shop 1 — PIN-0012 retires the
constant.

## Security decisions
- **No secret is stored on a user row.** Identity is `(provider, provider_user_id)`.
- **The session cookie holds a random 32-byte token; the database stores only its
  SHA-256.** A database leak then does not hand over live sessions.
- Cookie is `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` outside dev, with `Max-Age`
  matching the stored expiry.
- Logout **deletes the session row**, so it is revoked server-side rather than only
  forgotten by the browser.
- Expired sessions are rejected on read, not merely by cookie expiry — a copied cookie
  must not outlive its row.

## The LINE button
The login page shows LINE Login **disabled, with a reason**, because no channel is
configured yet. Same rule as PIN-0001: a control that cannot work must say so rather than
pretend.

## Review notes

The dashboard is behind a session, and the demo is still one click.

Verified against the built worker, every path:

| | |
| --- | --- |
| `GET /` with no cookie | 307 → `/login` |
| forged token | 307 → `/login` |
| after demo sign-in | 200, dashboard renders |
| logout | 303 → `/login`, and the **same cookie then 307s** — revoked, not forgotten |

Cookie carries `HttpOnly; SameSite=Lax; Max-Age; Expires; Secure` (Secure absent only in
dev). Confirmed in the browser that `document.cookie` cannot see it.

### The two security claims, checked rather than asserted
- **Only the digest is stored.** Signed in, then read `sessions.id` straight from the
  database: a 64-char hex string, not the cookie value.
- **The row is the authority on expiry.** Set `expires_at` into the past while leaving the
  cookie untouched; the next request redirected. A copied cookie cannot outlive its row.

A plain SHA-256 is deliberate rather than a password hash: the input is 256 bits of CSPRNG
output, so there is nothing to brute-force and slow hashing would only add latency to
every request. Recorded in `db/auth.ts` so it does not read as an oversight.

### A regression the tests caught
Gating the page broke 11 of 13 tests, and one of those was a **real defect, not just a
harness gap**: `getSession()` runs before `loadDashboard()`, so with the database down the
page threw past the `DataUnavailable` fallback PIN-0008 added. Session reading now happens
inside the same result-returning load function.

`redirect()` signals by throwing, so the anonymous case is returned as a value and acted on
*outside* the try — otherwise the redirect would have been swallowed as an error. `/login`
got the same treatment: a database outage shows the door rather than a stack trace.

The harness now signs in once in a `before` hook. The empty-database test needed a shop and
a user inserted — an empty database has no users either, and that test is about empty
*data*, not an empty user table.

### Logout had no button
The route existed and was tested, but nothing in the UI called it — a feature you cannot
reach is not done. The sidebar's store-menu button was a demo toast; it is now a real
logout form, and the card shows who is signed in (`คุณมะลิ`) instead of a hardcoded
"เชื่อมต่อแล้ว 3 ช่องทาง".

### LINE
The LINE button is disabled with a reason, per PIN-0001's rule. PIN-0014 implements the
provider once เกรพ has a LINE Login channel.
