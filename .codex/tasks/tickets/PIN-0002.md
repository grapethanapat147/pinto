# PIN-0002 — Cloudflare types and the D1 binding

**Type:** Chore · **Phase:** 2 · **Status:** Review

Spec: `.codex/specs/persistence-foundation.md` (first ticket of the breakdown; numbering
shifted because PIN-0001 was spent on the honest-states work).

## Goal
Nothing in the persistence milestone can be typed or tested until the Worker runtime
types exist and the D1 binding is switched on. Today:

- `npx tsc --noEmit` fails with 3 errors — `cloudflare:workers` unresolved in
  `db/index.ts`, and `Fetcher` / `D1Database` unresolved in `worker/index.ts`.
  `@cloudflare/workers-types` is not installed and is not available transitively.
  There is no `wrangler.toml`, so `wrangler types` cannot generate them either.
- `.openai/hosting.json` has `"d1": null`, and `vite.config.ts` only registers
  `d1_databases` when that field is truthy — so `getDb()` throws even locally.

No schema, no migration, no UI change in this ticket.

## Review notes

`npx tsc --noEmit` went from **3 errors to 0**, and it now covers `db/` and `worker/`
for the first time.

- Added `@cloudflare/workers-types@4.20260702.1` as a devDependency. It has no `types`
  or `exports` field, so TS resolves its root `index.d.ts` by convention.
- Wired it through a new root `worker-configuration.d.ts` (the filename `wrangler types`
  would generate) holding a triple-slash reference, **not** a `types` array in
  `tsconfig.json`. A `types` array would have disabled automatic `@types` inclusion and
  broken `process.env` in `vite.config.ts`, which relies on `@types/node` globals.
- `cloudflare:workers` exports `env` typed as `Cloudflare.Env`, which the runtime types
  leave empty on purpose for projects to extend. The same d.ts declaration-merges
  `ASSETS` and `DB` onto it, which is what makes `env.DB` in `db/index.ts` typecheck.
- `.openai/hosting.json`: exactly one line changed, `"d1": null` to `"d1": "DB"`.
  `project_id` byte-identical, no secret added.

### Binding proven, not assumed
A throwaway route returned `{"binding":"reached","rows":[{"ok":1}]}` — `getDb()` resolves
a real local D1 (miniflare, via wrangler 4.92.0) and executes SQL. Route deleted
afterwards; `app/api/` no longer exists and no app code touches D1 yet.

Two things learned while probing, both worth knowing for PIN-0003:
- **A folder under `app/` prefixed with `_` is not routed.** `app/api/_d1-probe` 404'd;
  renaming to `app/api/d1-probe` fixed it. Next.js private-folder convention, and vinext
  follows it.
- **D1 does not expose `sqlite_version()`.** The first probe failed on that, not on the
  binding — an easy false alarm to misread as a connection failure.

Nothing user-visible changed: a fresh tab loads the dashboard with zero console errors
and renders identically. `npm run build`, `npm run lint`, `npm test` (4/4) all pass.
