# PIN-0024 — Remove the unused OpenAI Sites target

**Type:** Chore · **Phase:** 6 · **Status:** Review

`.codex/specs/deploy-cloudflare.md` Q3 chose to leave `.openai/hosting.json` and the
`sites()` plugin in place "until a Cloudflare deploy succeeds", on the grounds that the Sites
route was merely *unknown* rather than ruled out.

Five Cloudflare deploys later, that condition is met. Keeping both means the repository claims
two deployment targets and a future reader has to work out which one is real.

## What it is actually doing
- `@openai/sites-vite-plugin` copies `.openai/hosting.json` and **all of `drizzle/`** into
  `dist/.openai/` on every build — 316 KB of artifact for a control plane nobody calls.
- `vite.config.ts` reads `d1` and `r2` out of that JSON to name the **local** miniflare
  bindings. So the file is not inert: deleting it without rewriting that is a broken build.
- `db/index.ts`'s error message tells the reader to set a field in it.

## Scope
Remove the plugin and the file, and replace the coupling with the literal values it was
providing. `git revert` restores it if the Sites route is ever wanted.

## Acceptance criteria
- [x] `sites()` and the `.openai/` import are gone from `vite.config.ts`.
- [x] The local D1 binding still works — dev server renders, local database intact.
- [x] `db/index.ts`'s message no longer points at a file that does not exist.
- [x] The dependency is removed from `package.json`.
- [x] CLAUDE.md no longer tells the reader to preserve it.
- [x] `npx tsc --noEmit`, `npm run build`, `npm run lint`, `npm test` (47) pass, and a deploy
      succeeded.

## Review notes

### The file was not inert, which is the part worth knowing
`vite.config.ts` read `d1` and `r2` out of `.openai/hosting.json` to name the **local**
miniflare bindings. Deleting the JSON without rewriting that would have broken the dev server,
not just removed a dead target.

### The trap inside the trap
`database_name` and `database_id` in that local config look like template leftovers and invite
tidying. **Miniflare derives the on-disk filename from them**, so changing either orphans the
local database — the seeded demo shop, and the LINE account granted access in PIN-0014. They
were therefore kept byte-for-byte and moved to named constants with a comment saying why. The
local database was backed up before the edit and checked after: same single file, 3 users, the
LINE account still named Grape.

### Measured
| | before | after |
| --- | --- | --- |
| `dist/.openai/` | 316 KB, including a copy of every migration | gone |
| dependencies | `@openai/sites-vite-plugin` | removed |

Deploy after the change: version `ad2dce87-f061-486a-8c63-39e4e3c4dc0c`, login 200, demo
sign-in renders from D1, LINE button live.

### Reversible
One `git revert` of this commit restores the file, the plugin and the coupling. That is
recorded in `vite.config.ts` itself, next to the constants, where someone wondering about them
will actually find it.
