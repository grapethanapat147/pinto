# PIN-0008 — Honest states when there is no data

**Type:** Feature · **Phase:** 2 · **Status:** Done

Spec: `.codex/specs/persistence-foundation.md` (milestone 5's remaining half).

## Scope split
The spec bundled two things under one ticket. Splitting, because they are unrelated in
risk and one is a live defect:

- **This ticket:** what the app does when the database is unreachable or empty.
- **PIN-0009:** seeding the 7 presentation tables with the 41 figures still hardcoded in
  components, and wiring the tiles to them (resolved Q1(c)). Pure data entry plus a
  presentational refactor — no robustness value, and it should not delay this.

## Two real defects, both measured
**1. D1 down = white screen.** Rendering with no `DB` binding returns **HTTP 500** and a
bare framework error page: `<html id="__next_error__">`, no Pinto shell, nothing in Thai,
no explanation. Every view is server-rendered now, so one unavailable binding takes the
whole product down with no message.

**2. An empty conversations table crashes the inbox.** `InboxView` opens with
`useState(conversations[0].id)`. That was safe while conversations was a module constant
that always had four entries; it is a live crash now the array comes from a query. Two
more lines index `conversations[0]` the same way.

Four views — Stock, Inbox, Growth, Money — have no empty state at all, so an empty (but
healthy) database renders bare headers over nothing.

## Acceptance criteria
- [x] A failed read renders a branded, Thai-language page explaining the situation rather
      than a framework stack page.
- [x] The failure page states plainly that no data is being shown — it must not fall back
      to fixtures and present stale demo numbers as live (the PIN-0001 rule).
- [x] The inbox does not crash on an empty conversations table.
- [x] Stock, Inbox, Growth and Money each render an empty state when their data is empty.
- [x] A seeded database renders exactly as it does today — this must be invisible in the
      normal case.
- [x] Tests cover the unavailable-database path and the empty-database path.
- [x] `npx tsc --noEmit`, `npm run build`, `npm run lint`, `npm test` pass.

## Review notes

### The unavailable page
`app/page.tsx` now loads through a `loadDashboard()` that returns a result rather than
throwing, and renders `DataUnavailable` when the read fails. Rendered and looked at, not
just asserted: Pinto's store mark, an amber warning, and a Thai explanation on the usual
ivory canvas — it reads like part of the product rather than a crash.

It deliberately **does not fall back to the fixtures**. Showing last-known demo numbers as
though they were live is the failure PIN-0001 removed from the buttons, and it is worse
here: a shop owner could act on figures that are not real. The test asserts no fixture
order id and no fixture money appear on that page.

The first version printed the raw error, which reads
`Set the \`d1\` field in .openai/hosting.json...` — developer-useful, but noise for a
merchant and a small leak of internal paths. Now gated behind `import.meta.env.DEV`, and
verified absent from a production build. That needed `vite-env.d.ts` for `ImportMeta.env`.

The first attempt used try/catch around the component body and lint rejected it
(`react-hooks/error-boundaries`) — correctly, so the loading moved out into a function
whose failure is a value to branch on.

### A live crash, fixed
`InboxView` opened with `useState(conversations[0].id)`. Safe while conversations was a
module constant with four entries; a crash as soon as the array came from a query and the
table was empty. Two sibling lines indexed `[0]` the same way. All three guarded, and
`sendReply` now returns early with no conversation selected.

Verified for real rather than reasoned about: the local database was emptied to schema
only, the page reloaded, and all five data views visited.

**Zero runtime errors** across all five. Server-side, an empty database returns 200 with

error condition.
