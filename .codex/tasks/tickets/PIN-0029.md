# PIN-0029 — Take PIN-0027 to production without deleting anything

**Type:** Feature · **Phase:** 8 · **Status:** Done

The deployed database was seeded on 12 Sep 2026: six hand-made orders, no order lines, no ad
spend, no product costs, migrations 0000–0005 only — and three users, one of them เกรพ's
granted LINE account. PIN-0027's code reads tables it does not have, so deploying it first
would break the Today card.

## เกรพ chose option 2 (2026-10-06): an additive backfill
Not `db:remote:seed -- --force`, which DELETEs every user including the LINE account.

## What was built
- `scripts/generate-history.ts` → `pricedHistory()`: the generated history priced and dated,
  shared by the seed and the backfill so the two cannot drift. Verified a pure refactor: the
  seed's SQL before and after is byte-for-byte the same size, with identical generated
  orders, `placed_at` values and ad spend.
- `scripts/backfill-history.ts`: the SQL. Inserts by natural keys (external id, SKU, channel
  code), never assumed ids; fills product costs only where empty; deletes nothing. Largest
  statement 37 KB, under D1's 100 KB limit.
- `scripts/remote-backfill.mjs` (`npm run db:remote:backfill`): reads the target and refuses
  unless it is exactly a pre-PIN-0026 seed — one shop, only the hand-made orders, all SKUs and
  channels, a last sync, no lines or ad spend yet (so it cannot run twice). Then `--dry-run`
  stops, or it asks for the database name, **records a D1 Time Travel bookmark and prints the
  restore command**, applies migrations 0006/0007, writes, and checks the result.

### Anchored to the database's last sync, not to today
History generated up to today would sit after production's last sync (12 Sep 15:09) and no
window would ever count it. Generated against the anchor, the deployed demo shows
"ข้อมูลถึง 12 ก.ย. 15:09 น." — the stale-but-honest state PIN-0027 designed. Making the demo
look current would mean moving `last_synced_at`, i.e. claiming a sync that never happened;
not done.
