# PIN-0021 — Seed the demo shop in production, once and safely

**Type:** Feature · **Phase:** 6 · **Status:** Done

Spec: `.codex/specs/deploy.md`, Q3. PIN-0020 established that migrations apply, so this
went ahead.

**The demo is live and signed into: https://pinto.grapethanapat147.workers.dev**

## The problem
A freshly migrated production database is empty, and that locks the front door rather than
merely emptying the room:

- The demo button looks up seeded `demo-owner` / `demo-staff` rows and returns 500 without
  them, so nobody can sign in at all.
- LINE refuses any identity that has no user row, by design (PIN-0014).
- `npm run auth:grant-line` writes to a local miniflare SQLite file **by path**. It cannot
  reach production, and should not be made to.

Under decision (a) the demo data *is* the product, so the deployment needs it.

## The design changed, and here is why

The spec chose **seed-on-empty inside the Worker**. Implementing it turned up the fact that
made that wrong.

**`scripts/seed.ts` is destructive.** It opens with `DELETE FROM` across 22 tables —
including `users` and `sessions` — and only then inserts the demo shop. That is correct for a
local reset and correct for a first run into an empty database. It is catastrophic anywhere
else: it removes every account that was granted access, including any LINE identity added
with `auth:grant-line`, and signs everyone out.

Seed-on-empty would have put that script behind an automatic check in the request path. A bug
in the emptiness check would not have meant "seeded twice", it would have meant **data
destroyed on a live visit**. The blast radius is wrong for the thing being protected against.

The second reason is that the spec's stated justification for the in-Worker design no longer
holds. `.codex/specs/deploy-cloudflare.md` Q5 kept it "so the ticket survives a change of mind
about hosting" — and hosting is now settled. `wrangler d1 execute --remote` exists on this
route and did not on the other.

So: **a guarded command, not an automatic write.**

## Design — `npm run db:remote:seed`

It reads the target database before doing anything and **refuses when it is not empty**. The
guard is a read of the real database, not a flag or a comment:

```
"pinto" already has 1 shop row(s), so it is not empty.

The seed starts by DELETEing 22 tables, including users and sessions. Running it here
would destroy every granted account and sign everyone out.

If that is genuinely what you want: npm run db:remote:seed -- --force
```

`--force` then requires **typing the database name**, so the destructive path cannot be
reached by an up-arrow and a return. A wrong answer writes nothing.

It also refuses, with a different message, when the `shops` table cannot be read at all — that
means migrations have not been applied, and the fix is a different command.

The spec's three properties are all still met, and without a write in the request path:

| property | how |
| --- | --- |
| empty-only | a read of the target, before anything |
| idempotent | a second run refuses rather than repeating |
| honest on failure | it says which failure and what to do, and writes nothing |

## The original design, for reference

The seed runs in the Worker when it finds an empty database, rather than through an endpoint
or a console. An endpoint that writes data is a thing to get wrong, and a guarded one is a
secret to manage; "only ever writes into an empty database" is a condition the code can check
for itself.

Three properties it must have, and the third is the one that takes care:

1. **Empty-only.** It writes nothing if any shop row exists. Never an upsert, never a repair.
2. **Idempotent under concurrency.** Two simultaneous first requests must not both seed. A
   `COUNT(*)` check alone is a race; the guard has to be a write that can only succeed once —
   a dedicated row with a unique constraint, inserted first, so the loser fails and backs off.
3. **Honest when it fails.** A half-applied seed is worse than none. If it cannot complete,
   the app should say the database is unavailable rather than serve a partial shop.

## Open questions for this ticket
- **Which fixtures?** `scripts/seed.ts` is the local seed and its timestamps are anchored to
  the run. Production should reuse it rather than growing a second copy that drifts.
- **Does it re-seed after a wipe?** "Empty-only" means yes, automatically. That is probably
  wanted for a demo, and should be a stated choice rather than an accident.

## Acceptance criteria

Rewritten alongside the design. Concurrency is no longer among them: a command run by a
person is not two simultaneous requests, and that criterion existed only because the original
design put the write in the request path.

- [x] The production database is seeded and the demo shop is usable.
- [x] A second run refuses rather than repeating — observed, not assumed.
- [x] The destructive path needs the database name typed; a wrong answer writes nothing.
- [x] A database whose tables are missing gets a different message pointing at migrations.
- [x] The demo sign-in works on the deployed URL, as both owner and staff.
- [x] `npx tsc --noEmit`, `npm run build`, `npm run lint`, `npm test` pass.

## Verified on the live deployment

| check | result |
| --- | --- |
| demo sign-in, owner | 303 with a session cookie |
| dashboard renders | greeting, shop name and figures all from D1 |
| shop name source | `ร้าน Mali Living`, read from the `shops` row |
| staff role gating | 0 Money nav items, 0 payouts in the payload |
| owner role gating | 1 Money nav item, 1 payouts |

The staff check needed care: a plain search for "การเงิน" finds it once even for staff,
because a seeded conversation has the topic **เอกสารการเงิน**. Matching the nav element and
the payload key instead gives the real answer — the same false positive that appeared during
PIN-0013.

## One more trap, recorded
`wrangler.deploy.json` was renamed to `.jsonc` so its comments could explain the filename
collision that `scripts/deploy.mjs` caught. Wrangler reads JSONC; `JSON.parse` does not, and
both scripts broke. `scripts/read-config.mjs` strips comments while tracking string state,
because a `//` inside a string is data.

## Remember
The deployed database is **public**. Anyone with the link is one button from being the shop
owner, with payouts and profit. Nothing real may go in it.
