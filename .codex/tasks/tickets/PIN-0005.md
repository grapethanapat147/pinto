# PIN-0005 — Read path: server/client split, orders and inventory from D1

**Type:** Feature · **Phase:** 2 · **Status:** Review

Specs: `.codex/specs/persistence-foundation.md` (D3), `.codex/specs/schema-v1.md`.
The spec calls this "the risky one" and says it should be reviewed on its own.

## Goal
`app/page.tsx` is `"use client"`, so the whole tree is client-side and every view reads
module-level fixtures. Turn the page into a server component that reads D1, and prove the
architecture on two domains (orders, inventory) before converting the rest.

## Plan
1. `db/queries.ts` — Drizzle reads mapped to the existing `app/types.ts` shapes, so views
   keep their current props and stay unaware of the data source.
2. `app/format.ts` — satang → `฿1,890`, ISO → `10:36` in **Asia/Bangkok** (the worker runs
   in UTC; the seed stored 10:36 local as 03:36Z, so naive formatting would be 7 hours out).
3. `app/page.tsx` → async server component; the current `Home` body moves to
   `app/components/AppShell.tsx` with `"use client"`.
4. `OrdersView` and `StockView` receive data as props instead of importing fixtures.

Inventory `status` is now derived, not stored (schema-v1 F2). Verified against the
fixtures: `on_hand = 0` → หมดสต๊อก; `days_left ≤ 7` → ใกล้หมด; else พร้อมขาย reproduces all
five rows.

## Known obstacle — the test harness has no D1
`tests/rendered-html.test.mjs` imports the built worker directly and calls
`worker.fetch(request, env, ctx)` with `env = { ASSETS }` — no `DB`. Separately,
`db/index.ts` takes its binding from the `cloudflare:workers` module, not from that `env`.

So the moment the page reads D1, all four tests are expected to fail. Resolving that is
part of this ticket, not a follow-up: a read path that cannot be tested is not done.
Approach to be determined empirically — measure the actual failure first rather than
guessing which of the two mechanisms bites.

## Review notes

The dashboard now reads orders and inventory from D1. `app/page.tsx` is 12 lines: an
async server component that queries and hands plain data to `AppShell`, which is the old
`Home` body moved wholesale with `"use client"` on it. Views were not rewritten — they
still take the same props, which is what D3 was for.

### The obstacle was not the one predicted
The ticket guessed the tests would fail on the missing `DB` binding in the harness's
hand-built `env`. The actual failure came earlier and harder:

```
Error [ERR_UNSUPPORTED_ESM_URL_SCHEME]: ... Received protocol 'cloudflare:'
```

`db/index.ts` imports `env` from `cloudflare:workers` at module scope. Plain Node cannot
resolve that specifier at all, so the lazily-imported page chunk blew up on load, before
any `env` was consulted. Measuring first rather than guessing was worth it.

Fix, all confined to `tests/support/`, nothing in app code:
- `resolve-hooks.mjs` — a module-resolution hook (registered with `node --import`) that
  points `cloudflare:workers` at a local stub.
- `cloudflare-workers-stub.mjs` — exports `env` as a Proxy over a global, so the test can
  install the binding even though the chunk reading it loads lazily mid-render.
- `d1.mjs` — a D1Database over Node 24's built-in `node:sqlite`, applying the real
  migration and the real seed to an in-memory database.

**Miniflare was tried first and rejected.** It gives genuine D1 semantics, but it boots a
`workerd` process: the probe ran past 120s without terminating. The shim keeps `npm test`
at ~250ms, and drizzle's d1 driver only touches prepare/bind/all/run/first/raw/batch.

### A test that can fail
The new case asserts seeded order ids, SKUs, satang-formatted money and the derived
`หมดสต๊อก` all reach the HTML. Falsified by disabling the seed in the harness: it fails,
the other four still pass — so it is testing the read path and not the layout. Seed
restored afterwards (`git checkout` could not do it — the file was still untracked).

### Lint caught a real bug
`orders` went from a module constant to a prop, so `useMemo(..., [query])` in `AppShell`
became stale-by-construction — order search would have frozen the moment the data changed
under it, which is exactly what PIN-0007's write path will do. Now `[orders, query]`.
