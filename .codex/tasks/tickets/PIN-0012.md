# PIN-0012 — Session-scoped data access, and an unauthenticated write API

**Type:** Feature · **Phase:** 4 · **Status:** Review

Spec: `.codex/specs/auth-and-roles.md`.

## The security hole this closes
PIN-0011 put the **page** behind a session. It did not touch the **API**. Demonstrated
against the built worker just now:

```
POST /api/actions/1/resolve   (no cookie at all)
 -> 200 {"resolved":true}
actions resolved by an anonymous caller: 1
```

Both write routes from PIN-0007 predate auth and check nothing. Anyone who can reach the
worker can resolve actions and post messages into a shop's inbox. Gating the dashboard
while leaving this open is worse than no auth at all, because it looks protected.

## The refactor
`SHOP_ID = 1` is a constant in `db/queries.ts` and `db/mutations.ts`, used at 21 call
sites. Each exported function takes the **session** instead, per the spec's decision to
thread it explicitly rather than through AsyncLocalStorage: an unscoped query then fails
to compile rather than silently reading someone else's data.

The session rather than a bare `shopId: number` because PIN-0013 needs the role at this
same layer, and a number is trivially passable by accident.

## Acceptance criteria
- [x] `SHOP_ID` no longer exists anywhere.
- [x] Every exported query and mutation takes the session and scopes to `session.shopId`.
- [x] Both write routes reject an unauthenticated request with **401**, writing nothing.
- [x] A second shop's data is unreachable with the first shop's session — proven with a
      real second shop and user, not by inspection.
- [x] Tests cover the unauthenticated write and the cross-shop read.
- [x] Every screen renders as it does today.
- [x] `npx tsc --noEmit`, `npm run build`, `npm run lint`, `npm test` pass.

## Review notes

### The hole is closed, retested the same way it was found
```
POST /api/actions/1/resolve        (no cookie)  -> 401   actions resolved: 0
POST /api/conversations/1/messages (no cookie)  -> 401   messages written: 0
```
Both routes resolve the session **before anything else**, and a rejected write leaves the
database untouched — asserted by counting rows either side, not just by reading the status.

### Cross-shop isolation, demonstrated
A real second shop was inserted with its own channel, order and owner. With shop 1's
session:

| | |
| --- | --- |
| its own `TT-10842` | visible |
| shop 2's `OTHER-SHOP-ORDER` | **not** present |
| shop 2's `ลูกค้าร้านอื่น` | **not** present |

Proving it with data actually in the table matters more than proving the `where` clause
compiles — an empty second shop would have passed regardless.

### The refactor did what it was designed to do
Removing `SHOP_ID` broke the build in exactly the right places: `tsc` listed every call
site that no longer had a shop to scope to. That is the whole reason the spec chose an
explicit parameter over AsyncLocalStorage — with ambient context those call sites would
have silently kept reading shop 1.

17 references in `db/queries.ts` and 3 in `db/mutations.ts` now read `session.shopId`. The
session rather than a bare number because PIN-0013 needs the role at this layer.
