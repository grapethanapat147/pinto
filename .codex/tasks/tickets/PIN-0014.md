## Where the secret goes — `.dev.vars`, not `.env.local`

I told เกรพ `.env.local` twice. **That was wrong for this stack**, and it was checked rather
than assumed: a temporary probe route read `Object.keys(env)` from `cloudflare:workers` with
a marker in each candidate file.

| file | reaches the Worker's `env` |
| --- | --- |
| `.dev.vars` | **yes** |
| `.env.local` | no |

`@cloudflare/vite-plugin` puts `.dev.vars` on the Worker env; Vite's own `.env.local` only
populates `import.meta.env`, which the server runtime here never reads for bindings. The
comment in `vite.config.ts` about "`.env*` files" is about Vite-level config, not bindings.

**`.gitignore` did not cover `.dev.vars`** — the pattern was `.env*`, which does not match
that name — so a secret placed there by normal Cloudflare convention would have been
committed. Fixed in this ticket, with `.dev.vars.example` carrying the non-secret keys.

## Design

### An unknown LINE user is refused, not provisioned
`users` rows carry `shop_id` and `role`. A first-time LINE account has neither. Auto-creating
one and attaching it to the existing shop would hand anyone with a LINE account the demo
shop's orders, customers and payouts — so the callback **refuses** an identity that has no
row, and says so.

To make that recoverable rather than a dead end, the refusal page shows the caller **their
own** LINE user id and the command that grants access. That is the only bootstrap path, and
it requires filesystem access to the project, which is the point.

### The ID token is verified by LINE, not locally
The token exchange returns an `id_token`. It is verified by POSTing to LINE's
`oauth2/v2.1/verify`, which checks the signature, issuer, audience, expiry and nonce against
the channel. Implementing JWKS verification locally would add a key cache and a signature
implementation to get the same answer, with more to get wrong.

### CSRF and replay
`state` and `nonce` are random per attempt, held in short-lived `HttpOnly` cookies, and both
are required to match on the way back. A callback with no state cookie, a mismatched state,
or a nonce LINE did not echo is rejected before any user lookup.

I told เกรพ twice to put the channel secret in `.env.local`. It was wrong, and finding out
turned up something worse. A temporary probe route read `Object.keys(env)` from

`.env.local` populates `import.meta.env` only, which nothing here reads for bindings.

**`.gitignore` did not cover `.dev.vars`.** The pattern was `.env*`, which does not match
that filename, so the file a Cloudflare developer would reach for by convention was
untracked-but-committable. Had เกรพ followed the normal convention instead of my wrong

`.dev.vars.example` carrying the two non-secret keys and an explicit warning.

The probe route was deleted once it had answered.

### เกรพ's console setup was verified, not assumed

The authorize URL Pinto builds was followed to LINE. It advanced to
`oauth2/v2.1/login?returnUri=/oauth2/v2.1/authorize/consent…`, which is the consent step —
LINE only gets that far when the channel id resolves **and** the `redirect_uri` is registered
on the channel. A wrong callback returns `invalid_request` instead. So channel 2011434259 and
`http://localhost:5173/api/auth/line/callback` are both correct.

The round trip past that point has **not** been exercised, because it needs the real channel
secret and I should not hold one. `.dev.vars` currently has the id and callback with the
secret blank, which leaves `lineConfig()` returning null, the login button disabled with its
reason, and `/api/auth/line/start` answering 503. That was checked, not assumed.

### An unknown LINE account is refused

`users` rows carry `shop_id` and `role`; a first-time LINE account has neither. Provisioning
one in the callback would hand any LINE account the shop's orders, customers and payouts, so
the callback answers **403** and creates nothing. The refusal page shows the caller their own
LINE user id and points at `npm run auth:grant-line -- <id> [owner|staff]`, which writes the
row locally. That path needs filesystem access to the project, which is the point.

The script validates the id shape (`U` + 32 hex) before writing, so a typo cannot become a
row that silently never matches a real sign-in.

### CSRF and replay
`state` and `nonce` are fresh per attempt, held in `HttpOnly` `SameSite=Lax` cookies for ten
minutes, and compared in constant time. Every exit from the callback — success, refusal,
LINE error — clears both, so a callback cannot be replayed. State is checked **before** any
database access, so a forged callback costs nothing.

### The ID token is verified by LINE
The exchanged `id_token` goes to LINE's `oauth2/v2.1/verify`, which checks signature, issuer,
audience, expiry and the nonce against the channel. Verifying locally would mean a JWKS cache
and a signature implementation to reach the same answer with more to get wrong.

### Tests
`tests/line-login.test.mjs`, eight tests. The network is stubbed rather than reached: these
assert Pinto's own decisions, not that LINE's servers work. Five were falsified individually
by breaking exactly what they protect — removing the state check, provisioning unknown
identities, reusing one state for every attempt, dropping `HttpOnly`, and showing the LINE
link when unconfigured. Each failed as expected and passes when restored.

The sign-in test also re-checks PIN-0011's rule still holds through this new path: the raw
cookie token never appears in the `sessions` row.
