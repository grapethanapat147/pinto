# PIN-0001 — Stop simulating success on controls that do nothing

**Type:** Feature · **Phase:** 1 · **Status:** Done

## Goal
`CLAUDE.md` requires that a toast never be presented as a successful marketplace,
inventory, payment or fulfilment action unless a real backend confirmed it. An audit of
`app/components/` found **27 controls** that break this, in three groups:

**A — claims completed work that never happened (9)**
`เตรียมใบปะหน้า 47 รายการแล้ว` · `นำเข้าข้อมูลตัวอย่างเรียบร้อย` ·
`สร้างรายการสั่งซื้อสินค้าไว้แล้ว` · `เพิ่มสินค้าทั้ง 3 รายการในใบสั่งซื้อแล้ว` ·
`อัปเดตข้อความล่าสุดแล้ว` · `อัปเดตข้อมูลแคมเปญแล้ว` · `บันทึกคำแนะนำไว้แล้ว` ·
`สร้างกลุ่มลูกค้าไว้แล้ว` · `เก็บรายการไว้จัดการภายหลัง`

**B — claims a screen opened that does not exist (11)**
the various `เปิด…` / `เลือกแคมเปญ …` toasts.

**C — dead controls with no handler at all (9)**
`เสร็จสิ้นแล้ว` · store menu · profile · region `ดูทั้งหมด` · `ไว้ทีหลัง` ·
`ดูสินค้าทั้งหมด` · `ดาวน์โหลดรายงาน` · calendar prev/next month.

Two further cases mutate demo state but overclaim: sending an inbox reply says
`ส่งข้อความถึง X แล้ว` when nothing reaches the customer, and resolving an action says
`บันทึกแล้ว` when nothing is saved.

`MoneyView`'s withdraw button is already honest (`นี่เป็นตัวอย่าง จึงยังไม่มีการถอนเงินจริง`)
and sets the house style to follow.

## Approach
Add a second toast tone rather than rewriting 27 strings into the same sentence. A
`demo` toast is visually distinct from a `success` toast, and its copy names what the
control *would* do before saying it is not active — so the demo stays informative to a
prospect watching a walkthrough.

Dead controls get wired to a demo toast too: a button that responds "not in this demo"
is better than one that silently does nothing.

## Acceptance criteria
- [x] `Notify` accepts an optional tone; `success` stays the default.
- [x] Toast renders visibly differently for `demo` vs `success` (colour + icon), in both
      the desktop and the ≤760px mobile layout.
- [x] No control claims a marketplace, inventory, payment or fulfilment action succeeded.
- [x] Every one of the 9 dead controls gives feedback.
- [x] Genuinely working interactions keep the success tone: period switch, reply
      validation warning, filters, search, navigation.
- [x] Inbox send and action resolve state plainly that the change is demo-only.
- [x] No layout, spacing or copy changes beyond the toast text and the new tone.
- [x] `npm run build`, `npm run lint`, `npm test` pass; `npx tsc --noEmit` no worse than before.
- [x] Verified at 1440 / 1024 / 760 / 390.

## Out of scope
Loading and error states for asynchronous data (there is no backend yet — that is the
rest of milestone 5, after `persistence-foundation`), and building any of the missing
screens.

## Review notes

Implemented as a second toast tone rather than 27 rewritten strings.

- `ToastTone = "success" | "demo"`; `Notify` takes an optional tone, defaulting to
  `success`, so no call site broke.
- `.toast.demo` is warm charcoal `#3b3531` with a light `#e8d9cc` badge and a lucide
  `Info` icon, against success green `#183c30` / `#6ac696` / `Check`. Verified computed:
  demo `rgb(59,53,49)`, success `rgb(24,60,48)`.
- Demo notices dismiss after 3600ms instead of 2400ms — they carry more to read. The
  dismiss timer now lives in a ref and is cleared on each new toast; previously a second
  toast inherited the first one's timer and could vanish early.
- 34 edits across 12 files. Copy pattern: `ตัวอย่าง — <what it would do> ยังไม่เปิดใช้งาน`,
  so a prospect watching still learns what the button is for.

Kept on the success tone, both verified as genuinely accurate:
- period switch — really does change the data (checked ฿48,720 → ฿286,940 on "7 วัน")
- `พิมพ์ข้อความก่อนส่งตอบลูกค้า` — real validation of real input

Behaviour deliberately unchanged: sending a reply still appends the bubble, resolving an
action still moves it and drops the badge 4 → 3. Only the claim changed.

Verified in the browser: 0 buttons without a handler remain (was 9); every formerly-dead
control returns a demo toast; both riskiest strings (inbox send, action resolve) confirmed;
1440 / 1024 / 760 / 390 all clean, and the longest string (72 chars) wraps to two lines at
390px without overflowing or colliding with the bottom nav.

`npm run build` ✅ · `npm run lint` ✅ 0 problems · `npm test` ✅ 4/4 · `npx tsc --noEmit`
unchanged (only the 3 pre-existing Cloudflare-types errors in `db/` and `worker/`, which
PIN-0001 does not touch and `persistence-foundation` schedules for PIN-0002's predecessor).
