# PIN-0007 — Write path: resolving an action and sending a reply persist

**Type:** Feature · **Phase:** 2 · **Status:** Done

Spec: `.codex/specs/persistence-foundation.md` (D4).

## Goal
Two interactions currently change React state and nothing else: resolving an action and
sending an inbox reply. PIN-0001 made them say so honestly ("ตัวอย่าง — … ยังไม่ได้บันทึกถาวร").
Make them real, then let the copy say so.

This is the ticket that makes persistence mean something: after it, a reload preserves
what you did.

## Approach (spec D4)
- `POST /api/actions/[id]/resolve` sets `resolved_at`.
- `POST /api/conversations/[id]/messages` inserts a message and bumps `last_message_at`.
- The client awaits the response and **only then** updates state and shows a success
  toast. A failure shows an error, never a success.

No optimistic UI. The existing `resolvedIds` / `sentReplies` state stays as the local
mirror of a write the server has already confirmed, so no full-page refresh is needed and
the current view is not lost. On reload the same rows come back from D1, so the mirror
and the database agree.

## Acceptance criteria
- [x] Resolving an action persists; after a reload it is still resolved and the Action
      Center total stays reduced.
- [x] Sending a reply persists; after a reload the message is in the thread.
- [x] Toasts switch from the `demo` tone to `success`, and only fire on a confirmed write.
- [x] A failed write shows an error and does **not** update the UI as though it worked
      (the PIN-0001 rule, now with a backend that can actually confirm).
- [x] Empty-message validation still rejects before any request is made.
- [x] Writes are scoped by `shop_id`; a bad id returns 404, not a 500.
- [x] Tests cover both routes, including the failure cases.
- [x] `npx tsc --noEmit`, `npm run build`, `npm run lint`, `npm test` pass.

### Honest by construction, not by copy
PIN-0001 made these two say "ตัวอย่าง — ยังไม่ได้บันทึกถาวร" because that was true. They now
carry the `success` tone, but only on the far side of an `await` that checked
`response.ok`. A failed request or a network error keeps the old state, shows a
neutral-toned failure, and does **not** append the bubble or move the action — the
PIN-0001 rule again, this time with a backend that can actually confirm.

`db/mutations.ts` returns a boolean for whether anything actually changed, so the routes
answer 404 rather than a misleading 200. Resolving twice is 404, not a silent second
success — the same principle at the API layer.

### No refresh needed
The existing `resolvedIds` / `sentReplies` state stays as a mirror of a write the server
already confirmed, so the current view survives. On reload the same rows come back from
D1 and the mirror is empty, so nothing double-counts. That avoided needing a
`router.refresh` equivalent, which vinext does not obviously provide.

Also fixed: `resolve_at` writes are scoped by `shop_id` **and** `resolved_at IS NULL`, so
a concurrent double-resolve cannot produce two successes.

### Tests: 6 → 9
A `post()` helper was added alongside `render()`. The new cases cover both routes, both
404s, the 400, and — deliberately first — a test asserting that a batch of *failed* writes
leaves the served total at ฿22,990, so a route that 500s into a partial write would be
caught. They run last and in order because they share the in-memory database.

The local demo database was re-seeded afterwards, so the dashboard is back to 4 open
actions and 6 messages for the next person who opens it.
